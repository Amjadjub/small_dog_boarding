# רשימת בדיקה ל־staging

## תשתית וסודות

- PostgreSQL מנוהל עם גיבויים אוטומטיים ובדיקת שחזור.
- `SECRET_KEY` אקראי נשמר ב־secret manager, לא בקוד או ב־Git.
- `DEBUG=False`, ו־`ALLOWED_HOSTS`, `CORS_ALLOWED_ORIGINS`, `CSRF_TRUSTED_ORIGINS` מכילים רק את הדומיינים בפועל.
- HTTPS בלבד; להפעיל `SESSION_COOKIE_SECURE=True` ו־`CSRF_COOKIE_SECURE=True` בפריסה.
- cache משותף (מומלץ Redis) עבור rate limiting כשיש יותר מתהליך backend אחד.

## דוא״ל

- חשבון SMTP ייעודי עם סוד בסביבת הפריסה וכתובת שולח מאומתת.
- להגדיר SPF, DKIM ו־DMARC בדומיין.
- לבדוק אימות חשבון, שליחה חוזרת, איפוס סיסמה, אישור, דחייה ועדכון שהות.
- לוודא שהקישורים מצביעים ל־`FRONTEND_URL` של staging ושאין פרטים רגישים בנושא ההודעה.

## פריסה ובדיקה

1. להריץ `python manage.py migrate` לפני פתיחת התעבורה לגרסה החדשה.
2. ליצור שני מנהלים נפרדים באמצעות `seed_admins` ולאמת שסיסמאותיהם שונות.
3. להריץ health check ותרחיש smoke מלא: אורח שולח בקשה → בעלים מאמת חשבון → הבקשה מקושרת → מנהל מאשר/דוחה → בעלים רואה התראה.
4. לוודא שמשתמש רגיל מקבל 403 מכל endpoint ניהולי ושבעלים אינו רואה מידע של בעלים אחר.
5. להפעיל לוגים וניטור שגיאות ללא סיסמאות, tokens או תוכן רפואי מלא.
6. לתעד גרסת image/commit ותהליך rollback; migration הפיך אינו תחליף לגיבוי.
